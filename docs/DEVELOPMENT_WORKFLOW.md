# 分支与开发流程

本文件是本仓库分支、源码归并和任务收尾的维护规范。README 提供入口，AGENTS.md 要求自动化开发遵守本文件；详细规则只在此维护。架构和源码归属见 [ARCHITECTURE.md](ARCHITECTURE.md)，页面信任与发布契约见 [PAGE_PACKAGE_UPDATE_PLAN.md](PAGE_PACKAGE_UPDATE_PLAN.md)。

## 1. 长期分支与版本

| 分支或引用 | 职责 |
| --- | --- |
| `main` | 唯一源码主线，汇总已审核且验证通过的成果；普通本地目录以它为日常基线 |
| `page-updates` | 页面更新渠道，仅由发布工具维护签名稳定索引；保持独立历史，不与源码分支互相合并 |
| `v<版本>` 标签 | 已发布 EXE 的固定源码身份 |
| `pages-v<版本>` 标签 | 已发布页面包的固定源码身份 |

不维护长期 `develop`、功能线或版本发布分支。合入 `main` 不等于已发布；生产版本以正式 Release、签名稳定索引和发布回执为准。已发布标签、签名清单所绑定的提交及历史回执保持不变。

## 2. 开工与任务分支

1. 先阅读本文件及相关模块文档，检查当前目录、分支、未提交文件和已有工作区。不得把其他任务的修改带入新任务。
2. 从远端更新引用，再同步干净的本地 `main`；只能快进，遇到本地独有提交或未提交改动先查明归属。不要用强制重置或清理命令解决同步问题。
3. 从最新 `main` 创建一个任务分支：`feat/<主题>`、`fix/<主题>` 或 `chore/<主题>`；主题用简短英文和连字符，可附日期或任务号。
4. 默认同时只处理一个任务。并行工作或保护已有修改时使用隔离工作区，记录其路径和对应任务；不要沿着已完成的旧功能分支继续开发。
5. 首次推送使用 `git push -u origin <任务分支>`，确保任务分支跟踪远端同名分支。

以下示例以工作区已干净为前提，`feat/example` 需要替换为实际任务名：

```powershell
git status --short --branch
git fetch --prune origin
git switch main
git pull --ff-only origin main
git switch -c feat/example
```

常用本地目录应保持可同步的 `main` 基线；单任务可以在该目录临时切换任务分支，完成后必须回到最新 `main`。隔离任务完成后也要同步常用目录，不能只更新隔离目录。

## 3. 验证、合并与本地同步

- 只暂存本任务明确审核的文件，不对混合工作区使用整体暂存。源码、依赖锁和确有变化的维护文档一起交付。
- 公共页面从官网的固定提交经 `sync-web-source.mjs` 同步；修改官网源码或桌面适配层，不直接手改已登记的生成快照。来源提交必须对应实际功能。
- 按改动范围验证。前端使用 `npm run check`；原生改动执行 Rust 格式、测试和 Windows 构建；纯文档修改检查链接、格式与差异。真实游戏验收、CI 构建和生产发布分别说明。
- 推送后创建目标为 `main` 的 PR，完成审核并确认必要 CI 成功。使用 merge commit 保留原提交身份；不得 squash/rebase 已发布或已签名引用的提交。
- 新页面校验器、公钥及其契约需先经审核进入默认分支。页面候选 CI 从默认分支读取可信工具，不能依赖只存在于功能分支中的工具。
- 合并后同步常用目录并核对 `main` 与 `origin/main` 一致、无未交代的修改；有依赖变化时重新安装依赖并执行适当检查。

```powershell
git switch main
git pull --ff-only origin main
git status --short --branch
```

## 4. 发布候选与权限

`page-candidates/<版本或批次>` 是短期发布输入，保存公开签名清单并触发页面工作流；对应的源码提交必须已在 `main` 中。候选元数据不作为主线常驻文件。私钥、用户数据、凭据和本地发布工作区不进入 Git。

合并源码只运行检查和构建，不自动取得生产发布授权。EXE 的 `v*` 标签，以及现有工作流支持的显式 `release/v*` 分支，都可能触发正式发布；仅在版本、范围和授权明确时创建。不要为普通同步创建这类引用。

已排队批次使用冻结的提交、路径和散列。即使代码已经合并，仍须等依赖该分支或工作区的批次完成并核对回执，才能清理。结果不明时先核对协调器和锁；不修改原批次、不删除监控锁，也不重跑已完成发布。

## 5. 归档与清理

- 已合并的任务分支，在确认无其他开放 PR、待发布批次或活动进程引用后删除；先核对本地工作区，包括未跟踪和忽略文件。
- 独有且仍需保留的历史使用 `archive/<日期>/<主题>` 标签或受控 Git bundle 归档，核对目标 SHA 后再删除分支。归档标签不是新的开发入口，不以新建长期归档分支代替清理。
- 旧 PR 已被替代时关闭并保留历史；以后需要其中的有效部分，从最新 `main` 新建任务分支移植。
- 临时工作区清理后，本地目录回到干净、同步的 `main`；保留必要的备份、签名材料和发布证据，并记录其去向。

## 6. 仓库设置

`main` 要求 PR 和 Windows 工作流的 `build` 检查通过，禁止强推和删除；使用 merge commit。开启合并后自动删除任务分支，本地分支和工作区仍需主动收尾。

`page-updates` 禁止强推和删除，但允许既有发布工具直接快进更新；不要给它增加源码 PR 或 Windows 构建门禁，以免阻断稳定索引发布。保护设置在 GitHub 配置，文档提交本身不会启用这些设置。

## 7. 完成定义

任务交付必须报告以下各项的实际结果：

1. **验证：**执行了哪些检查，哪些真实游戏或设备验收尚未进行。
2. **主线：**PR、合并提交及是否进入 `main`。
3. **本地：**常用目录是否已同步，是否还有未提交文件或独有提交。
4. **清理：**分支、工作区已删除或归档；保留项及其具体原因。
5. **发布：**未发布、已排队或已正式发布，分别提供对应证据。

仅推送功能分支、生成候选包或在隔离目录验证通过，都不能代替合并及本地同步。外部权限或发布引用阻止收尾时，明确列出剩余项，不将任务宣称为全部完成。
